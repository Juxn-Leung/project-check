# 建立与增量维护

## 接入

先读项目约束、需求与已有测试，检查工作区改动，保留用户工作。根据包清单、启动脚本、CI、路由、后端入口和数据库配置识别技术栈。不要读取并打印秘密值。

首次接入运行 `python3 <skill-dir>/scripts/project_check.py init --root <project>`。仅生成缺失的配置骨架，不覆盖已有文件。随后填写项目配置；空模板本身不是完成接入。

识别并保存：
- 项目根目录、前后端启动命令、执行目录、服务地址和就绪判断。
- 数据库、缓存、对象存储等实际需要的依赖及测试实例。
- 测试账号的环境变量名、隔离数据准备和清理方式。
- 原有单元/接口/浏览器运行器、选择特定用例的方法和原生报告格式。

命令以 argv 数组保存。需要 shell 功能时，优先调用项目已有脚本；记录执行目录、前置条件和可能的外部副作用。不要编造未验证的命令、地址或账号。

## 需求先于场景

按用户功能划分稳定模块 ID。先逐条登记已确认需求及其来源，再为需求建立场景映射。文件来源记录相对路径和 SHA-256；外部来源记录明确版本与确认依据；已确认的 OpenSpec 或用户请求可由 Codex 核对来源，不能每次强制人工重复确认。浏览器页内导航、按钮、表单、错误状态是扫描线索，不等于验收标准。代码推断标 `inferred`，无法明确预期标 `unknown`。有实质影响的不确定需求再向用户澄清，其余工作继续。来源未审阅或需求未映射时，不能称模块验收完整。

每个重要功能选择有意义的正常、异常与权限场景。例如创建记录需要覆盖入口点击、校验、提交、刷新后数据存在；适合由接口覆盖的权限边界无需在浏览器中重复穷举。

场景可以是 `unit`、`integration`、`browser`、`e2e`、`visual`。至少为关键前端流程建立真实交互测试。视觉基准需要已有认可依据或用户验收，不能将首次生成的截图直接当作设计正确性证明。

尽量复用既有测试。没有浏览器框架的常规 Web 项目可选 Playwright；具体安装、API、项目版本和运行环境先查项目文档/当前官方文档。不要强行迁移成熟的现有框架。为每个测试绑定稳定 scenario ID，可放在测试标题或运行器 metadata 中。

## 验证新测试

1. 运行测试发现/列举命令，核对文件、用例 ID 与清单一致。
2. 准备环境并试运行新增测试。产品缺陷可以导致失败，保留缺陷而不是让测试迁就实现。
3. 对关键或可疑断言，在隔离环境验证已知错误能使其失败。已有复现可以作为证据；需要临时注入时只改受控测试数据/响应，及时恢复。
4. 测试代码存在但未成功执行不等于有效覆盖；环境缺失记录阻塞。
5. 生成清单：`python3 <skill-dir>/scripts/project_check.py checklist --root <project>`。

## 增量更新

对照上次清单、需求差异、源码变更和现有测试识别受影响模块。保留场景 ID 和验收依据。修改描述、测试映射或模块依赖后重新校验；修改测试预期必须来自需求依据，不能仅引用修改后的实现。

删除功能时将场景设为 `retired` 并填 `retirement_reason`，保留历史。需要排除耗时场景时明确记录为跳过；不要从全量范围中无痕移除。

交付接入结果时报告模块数、需求数、未映射需求、场景数、已实现/缺失数量、试运行结果及待确认预期。不要用代码覆盖率替代关键用户流程覆盖。

## 项目理解与验收共用来源

首次接入时可同时建立 model.json，按 map.md 将功能连接到实际页面、组件、接口、函数和实体。模型引用 inventory 中的模块/需求/场景 ID；不要复制需求正文到另一份需维护的文档。标注仅静态推断的调用关系与尚未分析部分。先完善模型和 checks，再执行 snapshot；验收状态只在生成视图中绑定本次原生证据。

浏览器场景按 browser.md 接入 reporter，在 checks 中登记实际动作及结果断言。保留已有场景 ID 和测试；旧场景补充检查标记即可迁移。不要把自动发现的路由名称直接当作已确认功能。
